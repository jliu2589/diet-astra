## Setup needed from the owner

1. Supply the existing Supabase project's URL and **publishable** (or legacy anon)
   key in ignored `Config/Local.xcconfig`, using `Config/Local.example.xcconfig`.
   The `https:/$()/...` spelling avoids xcconfig's `//` comment syntax. Never use a
   service-role/secret key. Runtime config also rejects privileged keys.
2. Sign in to the Supabase CLI on your machine, link the existing project, review
   `supabase/migrations/202609200001_v1.sql`, then apply it. Its new tables use an
   `astra_` prefix and do not modify unrelated application tables. For the connected
   project above, reconcile migration history instead of reapplying. If those names
   already exist, reconcile the schema first; do not drop existing data.
3. In Supabase Auth, disable public sign-ups. Create two email/password users in
   Authentication → Users, one for each person. Confirm their emails through the
   dashboard as appropriate for this private app, give each their own password
   privately, and sign into the matching account on each person's phone. No IDs
   or emails are compiled into the app. Password recovery/admin changes currently
   use the dashboard; the app has no self-service signup/reset flow.
4. Set `OPENAI_API_KEY` and `OPENAI_MEAL_MODEL` in Supabase Edge Function secrets,
   not Xcode or Git. For example, `gpt-4.1-mini` supports image input and structured
   output ([model docs](https://developers.openai.com/api/docs/models/gpt-4.1-mini)).
   Deploy `interpret-meal`; its explicit Auth validation replaces the gateway's
   legacy JWT check (`verify_jwt=false`). Supabase URL/anon environment variables
   are supplied by the hosted function environment. Use an OpenAI API project with
   billing; a ChatGPT subscription is not the API configuration.
5. Choose your Apple signing team and a unique bundle identifier, enable HealthKit
   for that App ID, and provision/install on each physical iPhone. The current
   project requires iOS 27/Xcode 27; older iOS versions are not supported yet.

Typical non-secret commands, after CLI authentication:

```sh
supabase link --project-ref YOUR_PROJECT_REF
# Existing connected project: reconcile history as described above before db push.
supabase db push
supabase functions deploy interpret-meal
```

Set secrets through the dashboard or an ignored environment file; do not paste
secret values into repository commands, screenshots, issues or chat.

## Architecture and privacy

`AccountStore` owns authenticated data and serializes writes. `Backend` performs
Supabase I/O; SwiftUI uses store methods. Models are Codable values, calculations
are plain Swift, and the existing `DemoDiary` is a presentation adapter initialized
without fixtures for signed-in users. This is a small store/services arrangement,
not a new layered repository framework. The only added app package is the official
Supabase SDK and its transitive dependencies; native Charts renders graphs.

Auth tokens use the SDK's default Keychain storage. Loaded account/Health records
are in memory, cleared on identity change/sign-out. No offline mutation queue:
a failed save keeps the editor open and a stable UUID makes retries idempotent.
A failed refresh preserves the last loaded records with a retry message. Legacy
local `weights.json` is untouched, not silently imported into either account.

Health reads **bodyMass, stepCount, workoutType, activeEnergyBurned, appleExerciseTime**, with no write permissions,
background delivery or Apple Watch-specific code. Users initiate the read in
Settings or Weight journal. An empty read cannot reliably distinguish denial from
no data, and the UI says so. Manual weight days take precedence over Health days;
Health stays read-only and is never uploaded. Steps are summed by local day;
Health workout counts remain separate from strength logs to avoid double counting.
After an explicit connection, a local per-account preference enables read-only
refresh on launch/foreground and pull-to-refresh. Only that flag persists; Health
values do not. Disconnect disables refresh and clears the loaded snapshot; revoke
system read permissions in Apple Health. Each phone should be signed into its
owner's account before connecting that device's Apple Health data. Missing results
cannot prove whether read permission was granted. Failed refresh retains the prior
snapshot with a stale-data message and last-read timestamp.

### Connect a scale and activity on an iPhone

1. Connect/unlock the physical iPhone, trust the Mac and enable Developer Mode when
   Xcode requests it. Select it as the run destination. This project currently
   requires iOS 27. Select your signing team in Signing & Capabilities and provision
   the app with HealthKit enabled; Simulator ad-hoc signing is not device signing.
2. Enable Apple Health sharing in the scale's companion app. Verify an actual
   measurement appears in Health → Browse → Body Measurements → Weight before
   troubleshooting Astra. Exact scale-app controls depend on the manufacturer.
3. Run Astra on the iPhone and sign into your own account. Open menu → Apple Health
   → Connect Apple Health, then choose Weight, Steps, Workouts, Active Energy and
   Exercise Minutes as desired. Read access only; Astra never writes Health records.
4. Check the selected day in Apple Health and Astra, including workout duration and
   source. New scale readings appear after the scale app syncs; reopen Astra or
   pull to refresh. Active energy excludes resting calories and does not change
   your calorie target. Exercise minutes are not the sum of workout durations.
5. Manage access in Health → profile → Apps → Diet Astra. Test partial/denied
   permissions, app relaunch, a new scale measurement and Disconnect on the phone.

The Simulator has a separate Health database and cannot read the owner's iPhone or
Watch data. Physical installation and real-data validation are still pending.

## Tables and access

- `astra_profiles`: display name, one row per Auth user.
- `astra_goals`: nutrition/weight/training targets and signed intended lb/week.
- `astra_weights`: manual measurement timestamp and pounds.
- `astra_meals`: selected civil date, timestamp, foods JSON, notes, estimated flag.
- `astra_nutrition_days`: user-confirmed completeness for each date.
- `astra_workouts`: civil date, session title, validated exercise/set JSON.
- `astra_ai_usage`: daily count only, no request contents or images.

The first six tables use `auth.uid() = user_id` for both visibility and write checks;
anonymous access is revoked. All seven have RLS. Usage is accessible only through
the authenticated SECURITY DEFINER quota function with a fixed empty search path.
The function derives user identity from Auth, allows at most 60 requests per UTC
day, and performs its increment atomically. No service-role key is needed by the
app or meal function. Foreign keys cascade records on administrative account deletion.
A meal-change trigger reopens completeness on both affected dates.

## Meal pipeline

1. User types/dictates or selects/captures a photo and optional context.
2. Explicit Analyze sends only meal text/photo to the authenticated Edge Function.
3. The function verifies the bearer token with Supabase Auth, bounds the streamed
   body, accepts JPEG data only, and claims the user's daily quota.
4. OpenAI Responses uses strict structured output and `store:false`. It identifies
   foods/estimated grams and **per-100g estimated** nutrition separately. Refusals,
   incomplete/malformed responses and invalid bounds do not become saved meals.
5. Server code scales per-100g estimates to portions. Swift sums confirmed portions.
6. User edits food names, grams and portion nutrition, reviews uncertainty notes,
   then saves. No automatic AI save. Manual nutrition entry remains available.

There is no verified food database in this implementation. AI values remain labeled
estimates; use packaging/measured quantities to correct them. Changing grams in the
editor requires adjusting portion nutrition too, explicitly explained beside each
food. Photos/raw prompts are not persisted by Astra or written to application logs.
`store:false` is not a promise of zero provider retention; OpenAI's separate abuse
monitoring and image rules apply ([data controls](https://developers.openai.com/api/docs/guides/your-data)).

## Deterministic mathematics

- Portion totals: sum each saved food's calories/protein/carbs/fat. Round only after
  the daily sum for display. Week/month averages exclude missing meal days and
  include partial logged days; the UI explains that denominator.
- Weight: daily mean of available manual measurements, or Health if no manual day.
  The dashboard shows the latest selected-source measurement for that day. Trend
  weight averages available daily means from the seven calendar days ending at the
  last measurement. Rate is least-squares slope × 7 over the latest 28-day window,
  requiring seven measured days spanning at least 13 days. No interpolated weights.
- Projection: `(target − trend weight) / signed weekly rate × 7`, rounded up to days.
  Requires a measurement within 14 days, a rate toward the target, and a horizon
  under ten years. Intended and observed rate projections are separate estimates.
- Maintenance: require all 28 previous days marked complete with at least 500 logged
  kcal/day, at least 14 measured weight days spanning 21 days, and absolute observed
  rate no greater than 2 lb/week. Estimate `mean intake − rate × 3500 / 7`. Suppress
  estimates outside 800–6000 kcal/day or insufficient data. These are data-quality
  gates, not safe-intake recommendations. The estimate stays **preliminary**, never
  “high confidence.” Missing records produce a learning state.
- Once maintenance exists, calorie-target implied rate is
  `(target calories − estimated maintenance) × 7 / 3500`; its goal date is shown
  separately. It does not automatically adjust goals.
- This static energy-balance approximation is limited by water shifts, inaccurate
  logging, changing expenditure and metabolic adaptation. It is not a dynamic
  physiological model or prescription. See the [NIH explanation of limitations of
  the 3,500-calorie rule](https://newsinhealth.nih.gov/sites/newsinhealth/files/2016/January/NIHNiHJan2016.pdf).

  confirm records/totals. Sign out and sign in as B; verify an empty separate diary.

- Deny/allow Health reads on each phone. Confirm weights/steps/date boundaries and
  separation from logged strength workouts; check revoked permissions on refresh.
- Try typed ambiguous foods, dictation grant/denial, camera and library photos,
  context, AI corrections, failed analysis, repeated taps and expired sessions.
- Save in airplane mode: an error must preserve the draft; reconnect and retry.
  Refresh failure must not silently clear the last loaded diary.
- Inspect Today/Trends and forms in light/dark and large text with real sparse data.
- Review OpenAI estimates against known food labels before relying on totals.

Remaining scope limitations: no offline save queue, no persisted photo gallery,
no verified food catalog, no self-service account creation/password reset, no
automatic legacy-device-journal import, no real-time multi-device subscriptions.
Refresh/relaunch synchronizes records; this is appropriate for the initial private
app but concurrent edits use last server write. No Apple Watch UI or extra coaching.

  -only-testing:Diet-AstraUITests/LiveMealAnalysisTests/testTextAnalysisOpensEditableReviewWithoutSaving test

booted /absolute/path/to/fixture.jpg`. The verified fixture was
[Chicken and rice](https://commons.wikimedia.org/wiki/File:Chicken_and_rice.jpg),
